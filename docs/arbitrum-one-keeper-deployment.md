# Arbitrum One deployment and Cloudflare keeper

The mainnet deployment uses the address catalog in `scripts/constants/arbitrumOne.ts` and signing keys from Hardhat vars (`BRB_KEY`, `KEEPER_PRIVATE_KEY`, `INFRA_PRIVATE_KEY`, `MARKETING_PRIVATE_KEY`). It does not load `.env`, RPC overrides, recipient overrides, or CRE settings. The router is the real Uniswap V2 router. Production engine initialization uses predicted CREATE addresses for the registry, treasury and funder; referral and scheduler addresses are checked after deployment. Local tests still use isolated fixture contracts.

The marketing recipient, infrastructure recipient, house bot and dedicated keeper EOA are fixed in the catalog. Deployment validates all four entries and verifies the configured marketing, infrastructure and keeper signing keys. It stops before sending any transaction if one is missing or invalid. Do not substitute a random address, a test account or the administrator's account. New protocol addresses depend on the deployer's nonce; the script records actual deployed addresses in `deployments/arbitrum-one.json`.

## Commands

- `yarn check:dependencies:arbitrum` reads the configured Arbitrum RPC without a signing account and validates dependency code, token decimals, router factory and coordinator gas lanes.
- `yarn typecheck:deployment` checks the deployment entrypoints and their generated contract types.
- `yarn deploy:protocol:arbitrum` broadcasts the protocol deployment after preflight. Fund the deployer with ETH and LINK. The script supplies only approved gas shortfalls: keeper 0.005 ETH, infrastructure 0.001 ETH, and marketing enough to fund the house bot to 0.001 ETH while retaining at least 0.001 ETH plus a small transfer fee buffer. Native USDC is read only. Use the deployer exclusively for this release; concurrent sends invalidate CREATE predictions. A progress journal prevents blind reruns after any partial deployment. Configuration transactions are recorded in `arbitrum-one-transactions.jsonl`; inspect the signer's complete nonce range for subscription, CREATE and funding transactions after an interruption.
- `yarn seed:brb-usdc:arbitrum` creates and funds the real Uniswap V2 BRB/USDC pair with the explicitly approved 2,400,000 BRB and 24,000 USDC. Exact token approvals and minimum amounts protect that initial ratio. All minted LP goes directly to the deployer; no cliff or vesting contract is deployed or funded. Its journal prevents blind retries.
- `yarn verify:protocol:arbitrum` publishes the exact saved compiler inputs and verifies all 28 protocol deployments on Arbiscan, including the evaluator compiled inside SideBet and all proxies/libraries. It requires the explorer's authentication credential (`ETHERSCAN_API_KEY`); that credential is not an address or a contract-deployment input. Failed verification leaves `verificationComplete` false.
- `yarn deploy:cloudflare:arbitrum` bundles the actual manifest addresses, fixed RPC catalog and lane/market settings into the dedicated keeper. It uses Wrangler's saved OAuth login and uploads the dedicated `KEEPER_PRIVATE_KEY` and, when configured, `MAINNET_COUNTDOWN_WEBHOOK_SECRET` and `MAINNET_PAYOUT_WEBHOOK_SECRET` as secrets. It validates code, chain, cross-contract wiring, executor approval and keeper gas before uploading. The administrator key is rejected. Temporary secrets have restrictive file permissions and are removed in `finally`; no secrets are written under the repository's deployments directory.

## Adding the stablecoin markets

`yarn deploy:markets:arbitrum` adds USDC first (market 2), then DAI (market 3), to the existing BRB-first registry. It validates factory permissions, token decimals and registry wiring, estimates each transaction, waits for success, and checks the initialized banks. It does not transfer any stablecoins or change the BRB vault or DEX pool. A dedicated progress file and transaction journal prevent blind retries.

`yarn verify:markets:arbitrum` checks the new vault runtimes, beacon storage, market mapping, initialization, administrator roles and creation receipts, then verifies their proxy sources. `yarn verify:proxy-links:arbitrum` confirms all five proxy ABI associations. The Cloudflare keeper is then redeployed from the updated manifest with market IDs `[1,2,3]`.

USDC bank: `0x46206B1C1fc631Fd6Fcf2Aa2503f9cb022dA96bA`. DAI bank: `0x137dD55e422b1881Ad1566ce21E2E4F393bB37B2`. Both use the existing vault beacon and implementation. Minimum bets are 1 USDC and 1 DAI. They require deposited bankroll before accepting bets; DAI fee conversion also requires its direct DAI/BRB liquidity route.

## Worker operation

`cre-automation-starter/src/mainnet.ts` is a dedicated mainnet entrypoint. It imports no CRE execution code and does not depend on Goldsky webhooks. One SQLite-backed Durable Object owns the dedicated keeper EOA. Its alarm polls all configured scheduler lanes, handles roulette and SideBet jobs, waits for each receipt, and periodically processes each market's jackpot funding queue. A minute cron restores the alarm after outages. Transactions are signed and durably saved before broadcast; retries reconcile or rebroadcast the same transaction rather than silently allocating another nonce. A stuck transaction stops subsequent sends and makes readiness fail, so it requires operator recovery rather than accumulating conflicting transactions.

`GET /health` checks configuration and recent keeper execution. An unconfigured worker returns HTTP 503 and schedules no signing work. Authenticated `POST /webhook` and `POST /webhook/payout` accept wake-up hints only: payload calldata, round IDs and destinations never control signing. Both routes use the same existing Durable Object, and duplicate wake-ups are coalesced. Funding retry exhaustion is logged and makes readiness fail; an administrator must investigate and reset the appropriate retry, rather than the worker overriding the circuit breaker.

Provisioning uses `wrangler.mainnet-provision.jsonc`, with the real Biribi Cloudflare account and a dedicated mainnet worker name. It deploys the actual code and Durable Object without a cron, signer or contract catalog. Activation adds the real mainnet catalog, dedicated signing secret and cron through the validated deployment command. This does not modify the existing testnet watcher or its workflow bindings.

## Mainnet test architecture and liquidity

The `brb-test` deployment registers only BRB as market 1. Infrastructure receives 300,000 BRB and signs a deposit of all 300,000 BRB into its bank; infrastructure owns the vault shares. Marketing receives 300,000 BRB, then signs transfers of 1,000 BRB and the house bot ETH shortfall to `0xEc52D51bA55bef8108aeC20EbDeE79D84a443B7f`, retaining 299,000 BRB. The architecture phase reserves 2,400,000 BRB with the deployer for the separately authorized liquidity step. All deployer LINK is transferred to infrastructure. Infrastructure creates and owns the new VRF subscription, funds it with that entire transferred amount, and registers the engine as a consumer. Infrastructure receives the existing 2% infrastructure fee on positive house profit and the 1-token queued withdrawal fee. Deposits have no fee.

The architecture phase creates no DEX pair or stablecoin market and leaves USDC untouched. The owner subsequently authorized and completed the separate liquidity step: pair `0x848A51FaD11746bca839DF587C3Cde450bDfb853` holds 2,400,000 BRB and 24,000 USDC; its minted LP stays in deployer `0x90416a578646be1c3b2e6aa0A2F593445ca3Ebce`. No LP vesting lock is deployed or funded. The later stablecoin addition registers USDC as market 2, then DAI as market 3. Their banks are deployed and source verified, but start with no deposited bankroll. BRB jackpot funding works directly without a swap. SideBet contracts are deployed and wired; an offer catalog is a separate future step. Stablecoin markets need funded vaults and corresponding BRB liquidity before later activation.

Run the isolated rehearsal with `RUN_ARBITRUM_FORK=1 REPORT_GAS=false yarn hardhat test --no-compile --config hardhat.audit.config.ts test/MainnetBrbArchitecture.fork.test.ts`. It checks allocation, exact wallet funding, infra share ownership, BRB roulette settlement and direct BRB fee processing against the real Arbitrum router and coordinator. All writes stay on local chain 31337. Oracle fulfillment is simulated locally; this does not prove live DON delivery or hosted keeper operation.

Deployment and worker readiness are not launch approval. `activationApproved` stays false. The minimum ETH checks do not prove complete gas runway or LINK subscription sufficiency. Confirm bankroll, all funding routes, reviewed SideBet offers, indexer/frontend configuration, source verification, monitoring and bounded live acceptance transactions before launch. Existing contract-level audit findings and the repository-wide TypeScript failures are separate from this deployment-path check.

## Verification and recovery

`hardhat run --no-compile --config hardhat.audit.config.ts scripts/auditMainnetDeployment.ts --network arbitrum` is read only. It reconstructs expected constructor immutables and linked addresses and compares complete runtime bytecode, then checks proxy storage, contract wiring, administrator roles, bank ownership, VRF ownership/funding, pool receipts/reserves and LP ownership. Results are saved in `deployments/arbitrum-one-onchain-audit.json`. `yarn verify:proxy-links:arbitrum` confirms the explorer ABI links for the engine, SideBet and bank proxies without changing them on chain.

The architecture and pool funding rehearsals passed before their respective broadcasts. `reports/fork/arbitrum-one-brb-architecture.json` and `reports/fork/arbitrum-one-brb-liquidity.json` record the pinned blocks and limitations. The liquidity rehearsal used a fork of the actual deployed contracts. Saved mainnet private keys were not used to sign or broadcast transactions in either fork test.

Do not rerun a deployment or seeding command after a partial or uncertain result. Inspect its progress file, transaction journal, both signer nonce ranges, and actual receipts first. The LP lock remains an independent future decision; deploying its current contract starts a three-year cliff at deployment time.

## Optional RPC proxy authentication

The public RPC catalog works without extra credentials. To use the dedicated authenticated Cloudflare RPC proxy locally, store its `rpcProxyApiKey` in `scripts/constants/arbitrumOne.local.json` with file permissions 0600. This file is ignored by Git and contains no addresses or RPC URL overrides. No environment variable is used. Do not put the proxy credential in the public address catalog or commit generated Worker bundles containing an authenticated RPC URL.

## Optional Goldsky wake-ups

The same ignored credential file can hold `countdownWebhookSecret` and `payoutWebhookSecret` (at least 32 characters each, distinct values). The deployment command rejects the retired shared `keeperWebhookSecret` until migrated. It uploads the two route credentials as `MAINNET_COUNTDOWN_WEBHOOK_SECRET` and `MAINNET_PAYOUT_WEBHOOK_SECRET`, separately from the signing key. Goldsky's BRB project stores them in `BIRIBI_MAINNET_COUNTDOWN` and `BIRIBI_MAINNET_PAYOUT` HTTP authentication secrets with header `Authorization: Bearer <credential>`. The event mirror uses a third, independent `BIRIBI_MAINNET_MIRROR` credential matching frontend `MIRROR_API_SECRET`. Never commit credential values. See [webhook migration](https://github.com/BiribiNet/subgraph/blob/codex/publish-local-infrastructure-20261018/docs/webhook-authentication.md).

The existing `biribi-cre-countdown` and `biribi-keeper-payout` pipelines now read `arbitrum_one.raw_logs`, filter the actual mainnet engine, and call the mainnet worker's `/webhook` and `/webhook/payout` respectively. The former name is historical; neither pipeline invokes CRE. Each mainnet source uses a new checkpoint key and starts at `latest`; the subgraph owns historical accounting.

Cloudflare can propagate Worker and Durable Object code separately. Activation waits up to eight minutes for current keeper readiness and, when configured, the webhook secret readiness. Keep the existing Durable Object ID and storage through updates so pending signed transactions remain recoverable. A live mainnet betting/VRF/payout acceptance cycle is still a separate validation.
